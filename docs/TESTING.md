# Проверки и готовность

Загрузки Chrome UI: `node scripts/test-links-downloads.cjs <bootstrap.exe>
<new-output> <complete|cancel|interrupt|links>`. Используются синтетический TEMP-
профиль и loopback, CDP только в smoke. Проверяются штатные downloads-item и
их состояния, байты файла, реальные делегаты нативной кнопки/Ctrl+J (без физического
ввода), история и штатное закрытие. Снимок CDP показывает WebUI, не нативную панель.
Computer-use запрещён владельцем. [Результаты и ограничения](LINKS_DOWNLOADS.md).

На Windows запуск desktop smoke из ограниченной среды агента может приводить
к падению GPU-процесса с 0xC0000135 и завершению браузера с 0x80000003. Для GUI
использовать разрешённый запуск вне этих ограничений с отдельным тестовым профилем;
не отключать sandbox или GPU ради прохождения. При повторении сначала прочитать
журнал, не запускать цикл повторных падений. Контроль полного и сокращённого
комплекта CEF: [CEF_MODULARITY.md](CEF_MODULARITY.md).

Статус: добавлен исполняемый smoke-тест и начаты реальные запуски; отчёты находятся в docs/reports. Более широкая приёмка ниже остаётся планом, пока для неё нет отдельных результатов.

`scripts/smoke.ps1` проверяет создание браузера и native toolbar, загрузку главного frame с ожидаемым статусом, выполнение JavaScript локального fixture, callback закрытия, завершение CEF и отсутствие оставшихся процессов того же exe. Для произвольного URL проверка JavaScript fixture не применяется. Тест не проверяет изображение, ввод, sandbox-токены или взаимодействие с PDF; один HTTP 200 этого не доказывает. Используется отдельный profile-smoke, обычное окно должно быть закрыто.

После добавления собственной панели локальный сценарий также проверяет CEF is_drawn и размеры поля, установку иконок окна, вызывает тот же TextfieldDelegate для Enter и ButtonDelegate для назад/вперёд/reload. Переходы подтверждаются реальными документами и JavaScript-заголовками, reload — PerformanceNavigationTiming.type. Не используются реальные UI-нажатия; Ctrl+L/F5, кнопка остановки медленной загрузки и визуальное соответствие иконки требуют отдельной ручной приёмки.

Оконная часть smoke меняет размер на 900×600, разворачивает, восстанавливает, сворачивает и возвращает окно к исходным границам; состояние проверяется после каждой операции через CEF Window. Это проверка реального состояния окна через API, без мышиного перетягивания рамки и нажатий системных кнопок.

## Уровни

Реальная установленная копия и фактические Windows-токены проверяются отдельными
скриптами test-installed-files.py, test-installed-security.py и
inspect-test-process-tokens.ps1. [Результаты и открытый network sandbox](INSTALLED_VALIDATION.md).
Тесты используют новые временные профили и не должны обращаться к данным владельца.

Задержки первого HTTP исследованы отдельно: [HTTP_STARTUP_DIAGNOSIS.md](HTTP_STARTUP_DIAGNOSIS.md).
Диагностический runner поддерживает --net-log, --startup-trace и
--clone-test-profile <завершённый-успешный-smoke-output>. Эти режимы предназначены
для отдельных тестовых профилей. Сравнивать новый и подготовленный профиль нужно
раздельно: медленный HDD может задерживать создание SQLite-баз ещё до отправки GET.
Журналы остаются локальными и не считаются безопасными для автоматической публикации.

Навигационный smoke закрывает браузер после последней оконной проверки,
а не через фиксированные 30 секунд от создания окна. Отдельный watchdog
закрывает незавершившийся навигационный сценарий через 45 секунд; отсутствующие
маркеры всё равно означают провал. Для PDF/обычной загрузки остаются 30 секунд,
для проверки обновлятора — прежние 120 секунд. Внешний лимит runner для
навигации — 90 секунд с учётом запуска и завершения. Обычный запуск браузера
не затронут. Диагностический HTTP-сервер поддерживает управляемую задержку
первого HTML-ответа, а runner сохраняет временные отметки событий (наблюдение
с интервалом 50 мс только во время теста). Это не бенчмарк производительности.

- Unit: разбор адресов, разрешения, жизненный цикл и состояние; тестировать контракты и ошибки.
- Integration: профиль, адаптер движка, IPC, загрузки и права на локальных fixtures.
- GUI smoke: запуск, адрес, ввод, фокус, resize, DPI, popup, закрытие.
- Extension regression: матрица API и контрольные расширения из EXTENSIONS_POLICY.
- Security/privacy: sandbox, TLS, origin, отозванные права, повреждённые обновления и сетевые обращения.
- Performance: отдельные воспроизводимые измерения по BENCHMARKS.

CI сначала собирает и проверяет код. GUI и sandbox испытываются в подходящем Windows-сеансе; обычный headless runner не считается доказательством поведения desktop-приложения. Для неподдерживаемой платформы ставить «не проверено».

## Минимальная ручная приёмка

1. Чистый тестовый профиль, запуск и локальная страница.
2. URL, поиск, назад/вперёд, reload/stop и ошибочный адрес.
3. Ввод, кириллица/IME, выделение, clipboard, горячие клавиши и resize/DPI.
4. HTTPS и ожидаемый отказ для неверного сертификата; без обхода защиты.
5. Cookies и авторизация на тестовой учётной записи; файл upload/download.
6. Разрешение, отказ и отзыв доступа; popup и новая страница.
7. Сбой renderer и повторное открытие; обычный/приватный профиль.
8. Закрытие без оставшихся процессов и без повреждения профиля.

Реальные сайты: обычная страница, SPA, видео, PDF, формы и тестовая авторизация. Внешние сайты дополняют fixtures, но нестабильность сети не должна ломать весь детерминированный набор.

## Формат доказательства

Отчёт хранится в docs/reports/ после появления реальных запусков: дата, commit или идентификатор снимка, ОС/машина, версии движка и расширений, команды, сценарии, ожидаемое/фактическое, логи и ограничения. Не включать секреты. Для ручных действий явно писать «ручная проверка».

Готовность изменения: релевантные проверки прошли, diff просмотрен, документация согласована, ограничения указаны. Одна компиляция не доказывает запуск. Документационные изменения требуют проверки ссылок и согласованности, а не фиктивных runtime-тестов.


## Штатные внешние протоколы (Windows)

Проверки отдельного native-кандидата описаны в [EXTERNAL_PROTOCOLS.md](EXTERNAL_PROTOCOLS.md).
`pwsh -File scripts/test-native-external-protocols.ps1 -Executable <preview-exe> -OutputDirectory <new-output>`
регистрирует уникальную временную схему HKCU, компилирует handler, сохраняющий URI,
и удаляет регистрацию в finally. Используются новые TEMP-профили, loopback и CDP;
реальные приложения/профили и desktop input не нужны. Для результата нужны
`summary.json`, `result.json` каждого сценария, `tokens.json` и `fixture/cleanup.json`.

Появление native dialog подтверждается Tracing `Widget::Show` с
`layer=ExternalProtocolDialog`; несколько Show одного widget не означают несколько
диалогов. Flood отдельно проверяет один policy prompt и семь Chromium отказов.
Передача URI проверяется через заранее сохранённое разрешение только в тестовом
профиле. Это не проверка нажатий «Открыть»/«Отмена», визуального вида или DPI.
Неизвестная схема без handler не обязана показывать диалог.
