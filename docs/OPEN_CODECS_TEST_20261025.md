# Проверка AV1 / VP9 и hdrezka — 2026-10-25

Владелец предложил проверить hdrezka со сборкой AV1/VP9. Новая компиляция
Chromium для проверки не нужна: эти форматы уже включены в сохранённый stock
CEF 154.0.34 / Chromium 154.0.8037.98. Подготовлена отдельная диагностическая
копия alpha.7; основной media-кандидат alpha.8 не заменяется.

## Комплект и контроль

`dist/ChroMinimum-open-codecs-test-20261025/`: 25 allowlisted runtime-файлов,
383465620 байт; только en-US/ru, без профилей, PDB и инструментов сборки.
Критические SHA совпали с installer/seed-baseline-stock-alpha7.json.
AppContainer получил только inherited RX на runtime; sandbox/TLS не отключались.

`scripts/probe-open-codecs.cjs` запускает видимую локальную страницу в обычном
режиме с новым SSD TEMP-профилем. Воспроизводит два pinned Chromium fixtures
до ended, сохраняет counters/capabilities и закрывает только свой браузер
штатно. Полного сетевого лога и личных профилей нет.

| Формат | Фактический результат |
|---|---|
| AV1, bear-av1.webm | EOF, currentTime=2,702699 с, 82 frames, media error отсутствует |
| VP9/Opus, bear-vp9-opus.webm | EOF, currentTime=2,736 с, 82 frames, media error отсутствует |
| H.264 | canPlayType пусто, MSE=false |
| AAC | canPlayType пусто, MSE=false |

У обоих видео visibility=visible в начале/конце; браузер exit=0.
AV1 fixture побайтово сопоставлен с Git object закреплённого Chromium commit;
VP9 fixture совпал с прежним SHA из источников. Это короткая проверка
декодирования, не performance benchmark, не проверка физического звука
и не результат сайта.

[Сырые данные и lifecycle](reports/open-codecs-20261025/).
Один отдельный негативный CLI-тест подтвердил, что отсутствующий exe
завершает runner с кодом 1 без зависшего HTTP-сервера.

## Проверка сайта

Run-Hdrezka.cmd открывает предоставленную владельцем страницу с новым
TEMP-профилем. Дополнительно этот запуск выполнен агентом в обычном режиме,
без CDP/NetLog. Личные cookies, профили и пароли не копировались.
Автоматический доступ к защищённой странице не заявляется: если она требует
входа, нужны отдельные тестовые данные либо самостоятельная проверка
владельцем с сообщением только результата.

**Ручная проверка владельца не прошла.** 2026-10-25 владелец сообщил, что
после самостоятельного повторного запуска Run-Hdrezka.cmd плеер бесконечно
загружается. Это сообщение о наблюдаемом поведении, не автоматическая
идентификация кодека или доказательство отсутствия альтернативных потоков.
Локальное AV1/VP9 декодирование подтверждено, работа сайта — нет. Сетевые
потоки/точные кодеки, причины авторизации, сети и скриптов не исследованы.
Предыдущее подтверждение работы media alpha.8 относится к более раннему
ручному тесту, не одновременному парному сравнению на одинаковом сеансе.
Эта копия использует старую
оболочку alpha.7: её нельзя считать чистым сравнением только codec-параметров
с alpha.8 или новым релизом с её UI-исправлениями.

Если источник предоставляет только H.264/AAC, наличие AV1/VP9 его не
перекодирует. Для полного воспроизведения нужен также поддерживаемый
аудиоформат — одной подходящей видеодорожки недостаточно. Следующий вывод
о конкретных потоках делать только после наблюдения их metadata;
бесконечная загрузка сама по себе не доказывает конкретный codec.
Этот результат не даёт оснований компилировать ещё одну сборку с теми же
AV1/VP9. Обоснованный следующий диагностический шаг — определить форматы
видео/аудио либо повторить парный тест с media-кандидатом; перспективный
технический вариант H.264/AAC через системные API остаётся отдельной веткой.

## Дополнительные ошибки Console — 2026-10-25

Владелец предоставил текст Console открытого stock-теста. Зафиксирован
`net::ERR_NETWORK_CHANGED` одновременно у первого HLS `.ts` сегмента и
запроса сохранения прогресса `/ajax/send_save/`. Полные адреса CDN,
подписанные параметры и содержимое пользовательского сеанса не сохраняются.
Chromium определяет NETWORK_CHANGED (-21) как изменение сети:
https://github.com/chromium/chromium/blob/main/net/base/net_error_list.h

Это подтверждает сетевой отказ конкретных запросов, но не объясняет все
предыдущие повторения и не устанавливает кодеки потока. В предоставленном
фрагменте нет явной ошибки неподдерживаемого codec. Причина изменения сети
(например, VPN/интерфейс) не определена. Следующий контроль: при стабильном
соединении очистить Console, обновить страницу и повторить воспроизведение;
затем отдельно проверить свежие ошибки и metadata медиадорожек.

## Форматы фактического сегмента подтверждены — 2026-10-25

Из предоставленного владельцем локального HAR прочитано тело первого
сегмента, без повторных сетевых запросов. В HAR 271 запрос этого сегмента:
один HTTP 200 и 270 HTTP 304. Встроенное base64-тело имеет 135736 байт.
В MPEG-TS PMT найдены:

| PID | stream_type | Формат |
|---|---|---|
| 256 | 0x1b | H.264 / AVC |
| 257 | 0x0f | AAC |
| 258 | 0x15 | Metadata |

В данных также есть маркер x264. Значения stream_type сверены с локальным
закреплённым исходником FFmpeg `libavformat/mpegts.h` (строки 131, 140–141).
Таким образом, выбранный сайтом поток действительно H.264/AAC, а не AV1/VP9.
Оба необходимых формата отсутствуют в проверенной stock-копии (см. canPlay/MSE
выше). Добавление AV1/VP9 не обеспечит воспроизведение этого потока.
Это не доказывает отсутствие других вариантов на всём сайте и не исключает
сопутствующих ошибок; ранний ERR_NETWORK_CHANGED был отдельным наблюдением.

HAR остаётся только в ignored `.local/hdrezka.fi.har`; полные адреса,
заголовки, cookies и содержимое сегмента в отчёт не переносятся.
