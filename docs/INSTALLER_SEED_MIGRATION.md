# Миграция полного установщика на защищённое ядро, 2026-10-20

Основной alpha.4 setup создан после изолированной проверки перехода с legacy
active v1. Установленная копия владельца не изменялась: её состояние по-прежнему
active=1, highest=1, min_safe=1. Профиль владельца не читался и не запускался.

## Контракт перехода

`installer/seed-baseline.json` фиксирует уровень безопасности sequence=1 и
SHA-256 libcef.dll, chrome_elf.dll и CEF bootstrap chrominimum.exe для
154.0.34+g14c5a08+chromium-154.0.8037.98. Все три хеша повторно совпали с
публичными бинарниками реально установленного v1. Строка версии сама по себе
не даёт права присвоить уровень безопасности. Изменение этих трёх файлов
блокирует staging до пересмотра baseline. Это локальное решение для известной
сборки, не обещание автоматически определить security floor произвольного CEF.

Staging добавляет hash текущего адаптера, создавая installer-seed.json в seed.
Политика — доверенные данные полного установщика, а не подписанный receipt
format=1; она не поступает из сети. Закрытые ключи и рабочий канал не менялись.
Замена полного установщика/launcher/seed локальным атакующим не входит в эту
гарантию. Локальный setup по-прежнему без Authenticode.

Перед заменой файлов новый launcher извлекается во временный каталог и выполняет
`--installer-preflight <root> <new-policy>`. Он проверяет прежнее состояние,
security floor и эксклюзивные runtime leases под корневой блокировкой. Более
высокий floor, занятый runtime, повреждённое состояние или конкурирующая операция
блокируют установку. Механизм вызова: [Inno PrepareToInstall](https://jrsoftware.org/ishelp/topic_scriptevents.htm),
временные файлы находятся в начале списка для solid compression согласно
[ExtractTemporaryFile](https://jrsoftware.org/ishelp/topic_isxfunc_extracttemporaryfile.htm).

После копирования и ACL команда `--migrate-installation <root>` снова проверяет
floor/блокировки, хеширует четыре критических файла и атомарно сохраняет:

- active=0 (seed), pending=null, attempted=false;
- highest=max(прежний highest, baseline sequence);
- min_safe=max(прежний min_safe, baseline sequence);
- seed_policy_sha256 — идентичность проверенной политики.

Файлы прежнего v1 не удаляются. Для выбора seed теперь используется его
проверенный уровень из политики, а не техническое имя каталога «0».
При обычном запуске сверяются hash политики и DLL адаптера. Подмена/утрата
политики вызывает отказ. При выборе vN остаются подпись receipt и привязка DLL
к seed. Неудачный будущий v2 может вернуться на seed уровня 1 только при floor<=1;
при floor=2 запуск прекращается. highest при миграции не понижается, старые
последовательности обновлений не становятся новыми.

Старые state без нового поля продолжают читаться. Предыдущий launcher с
deny_unknown_fields откажется читать новое состояние: незаметный запуск старой
версии после downgrade не разрешается.

## Прерывания и ограничения

Весь Inno setup не является одной файловой транзакцией. Между preflight и
post-install проверкой возможен новый запуск или сбой копирования. Повторная
проверка/блокировки не позволяют записать успешную миграцию поверх используемого
ядра. Если копирование оборвалось, возможен отказ запуска из-за несовпадения
старого active и нового seed; нужно закрыть браузер и повторить тот же полный
setup. Это не автоматический откат всего установщика. Процессы принудительно
не завершаются, состояние и min_safe вручную удалять не нужно.

Основной setup ещё не запускался в сессии владельца. Тестовый вариант отличается
AppId/именем launcher/ключами регистрации, чтобы не затронуть настоящую установку.
Визуальное меню Windows и мастер вручную не принимались. Runtime взят из ранее
проверенной sandbox-копии; параллельные изменения UI исходников в него не включены.

## Проверки

31 обычный Rust-тест прошёл, включая три новых теста миграции: сохранение
highest=7/min_safe=1 с переходом на seed, повторная миграция/подмена политики,
отказ при floor=2/повреждении CEF/занятом runtime/root-lock без записи состояния,
успешная установка совместимого v2 и ограничение fallback порогом безопасности.
Два специальных fixture-теста пропущены по умолчанию. Release, clippy all-targets
с -D warnings, rustfmt, синтаксис Python и diff-check прошли. Ручное ревью путей
select/install/migrate выполнено; независимым аудитом оно не является.

Полный TestInstall подтвердил:

- floor=2: отказ до замены прежнего launcher/state и до создания seed/регистрации;
- EN: миграция legacy active=1/highest=1/min_safe=1, прежняя DLL-сентинел сохранена;
- RU: новая установка, тот же baseline=1, 8 pak против 4 в EN;
- HTML/JS → PDF/relaunch EN, PDF RU, штатное закрытие с кодом 0;
- фактический NetworkService AppContainer/Low, sandbox-type=network в обоих случаях;
- удаление, сохранение тестовых данных, неизменность UserChoice и основной
  Applications-регистрации в проверяемой сессии.

Legacy fixture содержит прежнее состояние и DLL-сентинел, а не запущенный старый
браузер. Совпадение реальных файлов CEF с baseline проверено отдельно выше.
Отрицательная проверка staging с другим bootstrap отклонила его до создания
выходного payload; все 34 хеша финального payload повторно совпали.
Компактные отчёты и токены: `.local/installer-migration-validation-2026-10-20/`.

## Расходы и артефакты

Новых зависимостей/служб/таймеров/сети нет. Полное хеширование CEF выполняется
при установке; при выборе seed — политика до 4 КиБ и DLL около 0,7 МиБ, буфер
хеширования 64 КиБ. Цена на HDD и RAM/CPU всего дерева отдельно не измерялись.
Launcher с иконкой 2448384 байта против 2420224 в предыдущем локальном payload:
+28160 байт (27,5 КиБ), не чистая парная сборка. Около 31 секунды browser smoke
включают намеренное 30-секундное окно проверки, а не время старта.

Основной `dist/ChroMinimum-0.0.1-alpha.4-local-setup-x64.exe`: 157929530 байт,
SHA-256 `6d6b03f3ce187159ce7413592989671bf10d3c695afc3a811cac18b5c25a9b25`.
TestInstall в `.local/installer-migration-dist-2026-10-20/`: 157929588 байт,
