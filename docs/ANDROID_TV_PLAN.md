# План: ChroMinimum для Android TV (Slimbox на Tanix W2)

Статус: **отложено владельцем 2026-11-22** (см. результаты разведки ниже).
Черновик плана, 2026-11-22. Код, каркас и зависимости не создавались.
Это не решение: ключевой выбор движка требует записи в DECISIONS.md после
спайка (этап 1) и согласования с владельцем.

## Целевое устройство (по вторичным источникам, не измерено)

- Tanix W2: Amlogic S905W2, 4×Cortex-A35, Mali-G31 MP2, Android 11, RAM 2 или
  4 ГБ (источники расходятся) — [androidpctv](https://androidpctv.com/tanix-w2/),
  [androidtvbox.eu](https://androidtvbox.eu/tanix-w2-is-an-android-11-tv-box-with-s905w2-soc-4k-av1-decoding/),
  [tanixtvbox](https://www.tanixtvbox.com/?p=2793).
- SlimBox ATV — сторонняя прошивка с интерфейсом Android TV (Android 9/11);
  у некоторых продавцов W2 поставляется уже с ней.
- Не подтверждено: ABI userland (arm64-v8a или armeabi-v7a), версия и
  обновляемость System WebView в SlimBox, реальный объём RAM у устройства
  владельца. Всё это снимается на этапе 0.

## Главное препятствие

Текущий стек (Rust + CEF/cef-rs) **не имеет Android-платформы**: официальный
CEF Android не поддерживает; существует только сторонний порт Cefrium.
Проект сам отмечает, что Android-сборка CEF — отдельная нерешённая задача
(CODEC_ALTERNATIVES_REVIEW). Поэтому «портировать как есть» невозможно;
нужен выбор движка. PRODUCT.md исключал мобильные версии из первого прототипа —
это расширение границ, нужно явное решение владельца.

## Варианты движка

| Вариант | Плюсы | Минусы / риски |
|---|---|---|
| A. Системный Android WebView (Chromium) | Нулевой вес поставки, аппаратное декодирование видео, обновляется отдельно | Версия зависит от прошивки; нет WebExtensions; Rust только через JNI; нарушает P01 «преимущественно Rust» |
| B. GeckoView | Современный независимый движок, расширения Firefox | +~60–80 МБ, другой движок, противоречит Chromium-ориентиру; нужны испытания |
| C. Cefrium (CEF for Android) | Ближе к текущему стеку | Сторонний, не проверен на актуальность версий и безопасность |
| D. Собственная сборка Chromium for Android | Полный контроль | Многочасовая сборка, поддержка патчей, огромный объём — несоразмерно хобби-проекту |

Предварительная рекомендация: **спайк на варианте A** (самый дешёвый и
реалистичный на слабом ARM-боксе), C/D — только если WebView в Slimbox
окажется непригодным. Не принимать решение до измерений.

## Этапы

**Этап 0 — разведка устройства (без кода).**
Через adb: `ro.product.cpu.abilist`, `getprop ro.build.version.sdk`, RAM
(`/proc/meminfo`), пакет и версия WebView (`dumpsys webviewupdate`),
поддержка H.264/VP9/AV1 (`MediaCodecList`), режим 1080p/4K, наличие Play
Store. Результат — отчёт docs/ANDROID_TV_DEVICE_PROBE.md.

**Этап 0б — диагностика «тяжёлого» видео (до выбора движка).**
Исходная претензия владельца: на W2 видео с hdrezka идёт тяжело даже в
Firefox при достаточной памяти. Память, вероятно, не узкое место; причину
нужно установить, а не предполагать. Матрица на одном и том же ролике 1080p:
1. Нативный плеер (VLC/Kodi/ExoPlayer-приложение) на прямом файле тестового
   видео с известным кодеком — предел железа: декодер, 1080p/30 и /60.
2. Тот же файл в `<video>`: Firefox, Chrome/WebView-браузер. Различие 1↔2
   = цена браузера; различие между браузерами = цена движка.
3. Страница сайта без видео: загрузка CPU от скриптов/рекламы (A35 слабые).
4. Метрики: `getVideoPlaybackQuality()` (dropped/total), `top`/CPU по ядрам,
   `dumpsys media.codec` — аппаратный или программный декодер; профиль H.264
   (High 4.1/4.2), частота кадров, режим вывода (SurfaceView или композитинг).
Гипотезы: программный декодер из-за профиля/DRM-пути; плеер сайта на JS
(MSE) грузит CPU; тяжёлые скрипты/реклама; перегрев/троттлинг; режим
экрана 4K с масштабированием. Выбор WebView/Gecko/другого — по результатам.

**Результаты разведки 2026-11-22 (adb по сети, только чтение; прошивка
Tanix_W2 11 RD2A.211001.002 2025080615, переустановлена после обнаружения
ботнета на старой прошивке).**
- SoC Amlogic S4, Android 11 (SDK 30), экран 1920×1080, RAM 3,5 ГБ
  (свободно ~1,4–1,6 ГБ), swap 1,7 ГБ.
- **Userland 32-бит: abilist = armeabi-v7a, armeabi.** Любая сборка движка —
  только под arm32; вариант D (собственный Chromium) практически исключён.
- System WebView 84.0.4147.125 (2020). Обновляемость (есть ли Play Store) не
  проверена. Firefox 157, armeabi-v7a.
- Аппаратные декодеры OMX.amlogic: H.264, HEVC, VP9, AV1, MPEG2/4.
- Во время воспроизведения в Firefox на новой прошивке: загрузка CPU ~45%
  (221% idle из 400%), процесс `media.codec` (hw OMX) активен, температура
  ~64 °C, частота 1,6 ГГц. Видео, по сообщению владельца, идёт нормально.
  Фактическое воспроизведение ролика на экране мной не наблюдалось.
- Вывод: исходная претензия (тяжёлый стриминг hdrezka) на новой прошивке не
  воспроизводится. Гипотеза, не проверенная: тормоза были из-за старой
  (заражённой) прошивки. Мотивация отдельной версии Android TV ослабла; её
  нужно подтвердить другой причиной (минимализм, пульт, приватность).

**Этап 1 — спайк движка (1–2 дня).**
Минимальный APK: один WebView с `LEANBACK_LAUNCHER`, загрузка тестовой
страницы, YouTube-подобное видео (HLS/MSE), fullscreen. Проверить: версия
Chromium в WebView, HTTPS/сертификаты, cookies, видео без дропов, память.
Если WebView устарел (<~100) — оценить B/C. Итог — запись D0xx в DECISIONS.md.

**Этап 2 — оболочка и ввод с пульта (D-pad).**
- Манифест: `android.software.leanback`, `touchscreen required=false`,
  banner 320×180, тема без тач-предположений.
- Курсор-режим: виртуальный указатель, управляемый стрелками (главная
  проблема браузера на ТВ); прокрутка по D-pad; переключение «курсор/фокус».
- Адресная строка + экранная клавиатура/голосовой ввод, Back = назад по
  истории, Menu = панель; крупные цели, overscan-безопасные поля.
- Без вкладок (в духе минимализма), один экран.

**Этап 3 — базовые функции.**
Профиль приложения, cookies, загрузки (минимально, DownloadManager или
запрет), popup-политика, блокировка небезопасного (sandbox WebView не
отключать, ошибки TLS не обходить), PDF — решить отдельно (в WebView нет
встроенного viewer).

**Этап 4 — производительность на W2.**
Замеры по BENCHMARKS: холодный старт, RSS/PSS на 2 ГБ, CPU в простое, сроки
загрузки тяжёлой страницы, дропы кадров видео. Сравнение с браузером,
идущим в SlimBox. Только измеренные утверждения.

**Этап 5 — упаковка и распространение.**
Подписанный APK (sideload, `adb install`/USB), отдельный ключ подписи,
версионирование, без Play-аккаунтов и телеметрии. Обновления — вручную или
через собственный релиз GitHub; фоновых служб не добавлять. CI: сборка APK,
lint, юнит-тесты логики курсора.

**Этап 6 (опционально) — Rust-ядро.**
Вынести общую логику (URL/поиск, политики, обновления) в Rust-библиотеку
через JNI, только если это оправдано замерами и не усложняет сборку.

## Влияние на ресурсы (ожидания, не замеры)

- Запуск/память: WebView-вариант — только процессы renderer/GPU на 2 ГБ;
  ожидается, что тяжёлые сайты упрутся в RAM. Проверить на этапе 4.
- Размер поставки: вариант A — единицы МБ; B ≈ десятки МБ; C/D — сотни МБ.
- Фон/сеть: ничего сверх запроса пользователя; автообновлений нет.
- Согласовать с владельцем перед реализацией (AGENTS.md).

## Риски

1. Устаревший/неподдерживаемый WebView в SlimBox → ограничения веба и безопасности.
2. Нет аппаратного декодера нужного кодека → тормозящее видео (AV1 заявлен, HEVC/VP9 проверить).
3. Управление пультом — основной UX-риск; нужен реальный прогон на ТВ.
4. Расширения (MV2/MV3) на Android WebView невозможны — зафиксировать в документах.
5. Сторонняя прошивка: не поддерживаем и не распространяем её; тестируем как среду.

## Критерии готовности (минимум)

Открывается из лаунчера ТВ; ввод URL пультом; сайт с видео 1080p играет без
заметных дропов; Back/выход корректны; сертификаты проверяются; нет
телеметрии; замеры занесены в документ; ограничения перечислены.

## Следующий шаг

Выполнить этап 0 на устройстве владельца (нужен adb: «Отладка по USB/сети»
в настройках разработчика SlimBox) и принять решение по границам продукта
(снять исключение «мобильные версии» в PRODUCT.md).
