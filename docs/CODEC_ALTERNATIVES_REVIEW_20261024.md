# Проверка альтернатив из пользовательского MD — 2026-10-24

Обращение в VIA отложено владельцем; черновик не отправлен. Текущий media-
кандидат сохраняется. Новая сборка CEF или смена архитектуры по этому обзору
не выполняется. Браузер задуман навсегда бесплатным, с добровольными донатами;
это модель распространения, не подтверждение патентного исключения.

## Системные декодеры

Это технически обоснованное направление. [Microsoft AAC Decoder](https://learn.microsoft.com/en-us/windows/win32/medfound/aac-decoder)
подтверждает системную реализацию. В проекте уже выполнены независимый
[MF probe](MEDIA_FOUNDATION_PROBE.md) и [эксперимент AAC внутри CEF](WINDOWS_PLATFORM_AAC_PATCH.md).
В успешном коротком прогоне подтверждены MediaFoundationAudioDecoder,
D3D11VideoDecoder, EOF видео, sandbox и shutdown. При этом WebAudio AAC
остаётся на встроенном пути; отдельные проблемы стартов/приёмки сохранены.
Это не готовая замена всей поставке FFmpeg.

Утверждение MD «лицензию оплачивают Microsoft/Apple/Google» нельзя трактовать
как универсальное освобождение издателя браузера от всех условий. Наличие
системного API подтверждает техническую возможность, а применимость прав
к конкретной дистрибуции требует отдельной проверки. VA-API/VDPAU также
являются интерфейсами; они сами не доказывают перенос всех обязательств.

## Почему двух GN flags недостаточно

В закреплённом Chromium 154.0.8037.98 [MimeUtil::AddSupportedMediaFormats](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/media/base/mime_util_internal.cc)
регистрация AAC/H.264 для MP4 и AAC/ADTS находится под USE_PROPRIETARY_CODECS.
Поэтому proprietary_codecs=false не является автоматическим выбором ОС-
декодера и не гарантирует работу обычных H.264/AAC веб-плееров. Нужны
проверенные изменения объявления возможностей и самих путей декодирования,
а затем повторные испытания. ffmpeg_branding=Chromium отдельно не решает это.

## Cisco OpenH264

[Бинарная лицензия Cisco](https://www.openh264.org/BINARY_LICENSE.txt) содержит
условия, при которых конкретный Cisco binary покрывается его AVC/H.264
соглашением. Это не общее разрешение для произвольного собственного H.264
декодера; AAC этим модулем не предоставляется.

[Mozilla объясняет](https://support.mozilla.org/en-US/kb/open-h264-plugin-firefox),
что OpenH264 в Firefox применяется для WebRTC, а обычное H.264 видео использует
системную поддержку. Это подтверждает разделение путей, а не возможность
просто положить DLL в CEF для работы всех MP4/HLS сайтов. Интеграция Cisco
binary в обычный HTML media path нашего CEF не выполнена.

## VP9 / AV1 / Opus

Поддержка этих форматов полезна, но не меняет формат, который отдаёт сайт.
Если источник отдаёт H.264/AAC и не предлагает альтернативный поток,
наличие VP9/AV1/Opus не обеспечивает воспроизведение этого потока.
Этот вариант не выполняет выбранное владельцем требование видео сам по себе.

## Что не следует смешивать

Условия распространения закодированного контента и поставки декодирующей
программы различаются. Тарифные исключения для отдельных streaming-сервисов
не следует автоматически применять к поставляемому браузеру.
Рецепт MD для «CEF на Windows/Linux/Android/macOS» также не подтверждает
единую реализацию: официальный [CEF](https://github.com/chromiumembedded/cef)
описывает Windows/Linux/macOS; Android-платформа проекта остаётся отдельной
задачей. Здесь ни Android-сборка, ни новая система загрузки кодеков не создавались.

Следующий технический шаг после сайта, если владелец вернётся к этой ветке:
оценить оставшиеся AAC/WebAudio пути и воспроизводимость системного backend
на текущем Windows, до новой полной сборки Chromium. Прежде чем реализовывать,
отдельно согласовать стоимость и границы изменения.
