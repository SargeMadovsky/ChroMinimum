# Диагностика задержки первого HTTP, 2026-10-20

Причина воспроизведённой задержки — дисковая инициализация нового профиля CEF
на E:, включая доступ сетевой sandbox к каталогу и создание SQLite-базы cookies.
Это подтверждено NetLog, startup trace и контролем с тем же executable/CEF,
но профилем на C: или копией уже созданного тестового профиля на E:.
Доля нагрузки от антивируса, конкурирующего I/O и файловых фильтров не измерена;
не утверждается, что любой HDD всегда даст 30 секунд.

## Условия и результаты

Windows x64, CEF 154.0.34 / Chromium 154.0.8037.98. Один диагностический runtime
в `.local/http-delay-diagnosis-2026-10-20/bundle`, никаких реальных профилей.
Тестовая страница отдаётся ThreadingHTTPServer по 127.0.0.1. Основная серия
последовательная, сборка/хеширование пакетов параллельно не запускались.
Системные proxy, sandbox, TLS, шифрование cookies и настройки антивируса не менялись.

Через Windows Storage API прочитаны модели: C: — Samsung SSD 990 EVO Plus 1TB,
NVMe; E: — TOSHIBA HDWD240, SATA, HDD по Get-PhysicalDisk. Оба сообщают Healthy;
это не углублённая проверка состояния накопителя.

| Прогон | Профиль | Первый GET от старта процесса | Загрузка cookies по NetLog |
|---|---|---:|---:|
| baseline, HTML/навигация | Новый E: | 3,587 с | 1266 мс |
| baseline-locale | Новый E: | Не отправлен до watchdog | Не завершилась |
| trace-html | Новый E: | 2,720 с | 1196 мс |
| trace-locale | Новый E: | 29,891 с | 14279 мс |
| warm-locale | Копия созданного trace-locale, E: | 0,295 с | 16 мс |
| fresh-e-repeat | Новый E:, повтор | 2,624 с | 1385 мс |
| control-c | Новый C:, runtime остаётся E: | 0,281 с | 34 мс |
| control-c-repeat | Новый C:, повтор | 0,284 с | 34 мс |

Все прогоны, кроме baseline-locale, прошли свои smoke-проверки. У неуспешного
baseline-locale процесс завершился с 0, но получен ERR_ABORTED без загрузки страницы:
его закрыл существующий 30-секундный smoke-watchdog. Это не падение 0x80000003.
Остаточных chrominimum-процессов после серии нет.

Release DLL собрана; clippy --all-targets с -D warnings, rustfmt, синтаксис двух
Python-скриптов и git diff --check прошли. Анализатор выполнен на сохранённых
логах восьми прогонов. После runtime-серии вложенные диагностические if объединены
в эквивалентные условия по замечанию clippy; эта правка повторно собрана и проверена
статически, без новой серии браузерных запусков.

Для trace-html/trace-locale/warm-locale/control-c включались NetLog и startup trace,
для остальных только NetLog. Трассировка влияет на I/O, поэтому это диагностика,
а не парный бенчмарк, и величины нельзя переносить на обычный запуск/все сайты.
Повтор E: оказался существенно быстрее медленного прогона: вероятны влияние
прогрева и изменяющейся дисковой нагрузки, но точная их доля не установлена.

## Где находилось ожидание

В trace-locale `GrantSandboxAccessOnThreadPool` занял 15181 мс. Это подготовка
каталога для сетевой sandbox, а не основание отключать её. В контролях он занял
11 мс на копии профиля E: и 36 мс на новом профиле C:.

Сервер принял соединения примерно через 15,6 с. Далее NetLog показывает:

1. Созданы URL request и запрос к постоянному хранилищу cookies.
2. 14279 мс ожидается `COOKIE_PERSISTENT_STORE_LOAD`.
3. После его завершения за 1–2 мс начинается отправка HTTP.
4. Заголовки ответа получены в том же миллисекундном интервале NetLog.

На потоке хранилища трасса показывает 14277 мс в
`SQLitePersistentCookieStoreBackendBase::InitializeDatabase`, включая
PathExists 2006 мс, sqlite3_open_v2 1224 мс, commit 3824 мс,
CREATE TABLE cookies 3437 мс и CREATE UNIQUE INDEX 2254 мс.
Параллельно видны многосекундные создания других баз нового Chrome-style профиля,
например истории. Нет свидетельства, что 14 секунд ушли на криптографию.
`KEY_LOAD` в NetLog обозначает ключ выборки cookies по домену, не ключ шифрования.

В коде Chromium [URLRequestHttpJob](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/url_request/url_request_http_job.cc)
получение cookies предшествует StartTransaction; в
[SQLitePersistentCookieStore](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/extras/sqlite/sqlite_persistent_cookie_store.cc)
видны асинхронная загрузка и доменный keyed load. Ссылки объясняют механизм
по main, а фактические длительности и имена функций взяты из исполняемого CEF 154.

Следовательно, у воспроизведённой медленной загрузки основное ожидание возникло
до отправки GET. Python-сервер, чтение ответа, DNS и proxy-resolution не объясняют
этот интервал. Это не утверждение об отсутствии любых других сетевых задержек.

## Инструменты и ограничения

В src/lib.rs добавлены только smoke-переключатели `--test-net-log` и
`--test-startup-trace`. Вне `--smoke-test` они не активируются. Журналы пишутся
в выбранный тестовый data-dir; экспорт наружу не добавлен. Startup trace ограничен
60 секундами, в этой серии файлы содержат десятки МиБ. Зависимостей и службы нет.
Локальная Release DLL до/после задачи: 708096 → 712192 байт (+4 КиБ);
это сравнение артефактов, а не чистая парная сборка. Накладные расходы диагностических
режимов на CPU/RAM отдельно не измерялись. Без явных флагов журналы не включаются.

Runner `scripts/smoke-component-bundle.py` сохраняет отметки принятия соединений
и позволяет `--clone-test-profile` из завершившегося успешного smoke. Источник —
созданный нами profile-smoke, не пользовательский профиль. Создаётся отдельная копия.
Итоговая длительность locale-теста около 30 секунд сама по себе не является временем
загрузки: тест намеренно держит окно до прежнего 30-секундного таймера.

Пример воспроизведения на новом каталоге:

```powershell
python scripts/smoke-component-bundle.py --bundle <diagnostic-bundle> --output <new-output> --case locale --net-log --startup-trace
python scripts/summarize-http-startup.py <new-output> --output <new-summary.json>
```

Все локальные отчёты серии и comparison.json находятся в
`.local/http-delay-diagnosis-2026-10-20`. Контроли C: дополнительно скопированы туда
как control-c/control-c-repeat; исходные тестовые каталоги во временной папке C:
сохранены. Исходные E2E-архивы/receipt из предыдущих этапов не менялись.

NetLog дополнительно обнаружил стандартные фоновые запросы Chrome-style CEF,
включая content-autofill.googleapis.com. Это отдельный открытый пункт политики
отсутствия скрытых соединений; в рамках этой диагностики такие сервисы не отключались
и отсутствие фоновой сети не заявляется.

Следующий шаг: при проектировании инсталлятора отделить каталог программы от
пользовательского data-dir и выбирать обычный per-user LocalAppData, учитывая
возможность перенаправления на HDD. Для тестов разделять новый и подготовленный
профили, не маскируя время первого запуска увеличением watchdog.
Перенос существующих данных и изменение production-пути в этой задаче не выполнялись.
