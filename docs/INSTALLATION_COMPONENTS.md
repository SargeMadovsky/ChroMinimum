# Компоненты установки и выборочные обновления

Дата: 2026-10-20. Область: Windows x64. Реализована проверка локальной
конфигурации и построение плана без загрузки/установки. Инсталлятор, запись
настроек полноценным UI и сетевая установка модульных обновлений пока не реализованы.
Добавлены проверка подписанного каталога, выбор пакетов и офлайн-сборка
нового комплекта без сети и переключения действующей установки.
Существующий канал обновлений format=1 продолжает доставлять полный комплект.

## Проверяемый выбор

Будущий инсталлятор сохраняет намерение пользователя в `installation.json`
в корне установки, вне каталогов версий ядра и вне профиля сайта. Пример:

```json
{
  "format": 1,
  "ui_locale": "ru",
  "locales": ["ru"]
}
```

Локальная конфигурация не является подписанным каталогом пакетов и не разрешает
загрузку/исполнение произвольных файлов. В ней нет URL, путей, ключей подписи,
настроек защиты или идентификаторов произвольных нативных модулей.

Реализованный `updater/src/components.rs`:

- принимает не более 4096 байт и только format=1;
- допускает только проверенные языки ru и en-US, отвергает неизвестные поля,
  повторные поля JSON, повторные языки и основной язык вне выбранного списка;
- всегда включает обязательное ядро и резервный en-US;
- формирует стабильный порядок без дублирования: ядро, en-US, затем ru при выборе;
- не добавляет орфографию, доступность или другие неподтверждённые компоненты.

Для русского примера план содержит core, locale/en-US и locale/ru. Для английского
выбора — core и locale/en-US. Идентификатор locale в плане описывает данные CEF,
а не готовый перевод собственных кнопок оболочки. PDF пока входит в обязательный
комплект по PRODUCT.md. Доступность остаётся внутри существующего бинарника CEF;
отсутствие её в перечне не означает физическое удаление кода.

Команда только чтения, выполняется до запуска CEF и до обращения к каналу:

```powershell
./updater/target/release/cm-update.exe --components-plan installation.json
```

Некорректный файл даёт ненулевой код, без окна ошибки и без подмены выбора
значениями по умолчанию. Сам файл команда не создаёт и не меняет. Обычные запуск
и обновление пока не читают эту конфигурацию. Изменение поля в JSON сейчас не
меняет состав установленного браузера.

## Контракт будущего каталога обновлений

В `updater/src/catalog.rs` реализован отдельный подписанный формат каталога;
его публикация и установка ещё не подключены. Расширять manifest=1
неизвестными полями нельзя: текущий клиент отвергает их. Для старых клиентов
сохраняется прежний канал до явного перехода на новый загрузчик. Новый
инсталлятор должен поставляться с клиентом нового формата. Автоматическое
превращение существующей полной установки в минимальную не предполагается.

Каталог должен подписывать полный перечень пакетов и связывать каждый с одной
поставкой: sequence, platform, точная идентичность CEF/адаптера, ID компонента,
размер архива, SHA-256 и допустимый HTTPS-источник. Совпадения только milestone
недостаточно. Пакеты разных поставок смешивать нельзя. Сроки, минимальная
безопасная sequence, ограничения источника и защита от отката сохраняются.

Приёмка должна включать отсутствие незапрошенных языков в списке загрузок.
Резервный en-US — явно документированная зависимость, не скрытая дополнительная
функция. Если для выбранного языка в выпуске нет совместимого пакета, установка
кандидата отклоняется с понятной ошибкой; нельзя молча сбросить язык или навсегда
заблокировать доставку security fixes без сообщения пользователю.

## Сборка и переключение комплекта

### Реализованная проверка каталога

Внешний JSON-конверт использует существующие поля payload/signature и Ed25519.
Подпись проверяется по точным байтам строки payload до разбора каталога. Лимит
всего конверта — 64 КиБ. Поля payload: format=2,
purpose="chrominimum-components", launcher_api=2, platform="windows-x64",
sequence, min_safe_sequence, engine_version, adapter_sha256, issued, expires,
packages. Каждый пакет содержит component (объект kind=core либо kind=locale
с locale=ru/en-US), sequence, engine_version, adapter_sha256, url, size, sha256.
Все поля обязательны, неизвестные поля и ID отвергаются.

Сейчас каталог содержит максимум три пакета: core и два проверенных языка.
Для каждого проверяются идентичность выпуска, хеши SHA-256 по 32 байта,
размер от 1 байта до 512 МиБ, источник собственного GitHub-репозитория с ровно
двумя безопасными сегментами после releases/download. Дубли компонентов/URL,
query, fragment, escape-последовательности и traversal отвергаются.
Обязательное ядро должно присутствовать. Отсутствующий язык блокирует только
план, которому он нужен; резервный en-US обязателен для любого плана.
Сумма выбранных архивов ограничена 512 МиБ.

Проверка sequence учитывает переданные highest/min-safe, не позволяет снизить
известный порог безопасности, принимает тот же выпуск для будущей смены языка.
Срок не более 45 суток; будущее issued допускается с запасом 300 секунд.
Непроверенный Catalog не может сформировать план: это метод VerifiedCatalog,
который создаётся только после проверки подписи и полей. Проверка metadata
не доказывает содержимое архивов: скачивание, сверка реальных байтов и
ограничения файлов при распаковке остаются следующим этапом.

Диагностическая команда без записи и сети:

```powershell
./updater/target/release/cm-update.exe --catalog-plan installation.json signed-catalog.json 10 8
```

Числа 10/8 здесь — явно заданные параметры проверки highest/min-safe. Команда
не изменяет сохранённый state и не управляет действующим обновлением.
Используется встроенный публичный ключ; тесты подписывают временным ключом,
не читают рабочий закрытый ключ и не публикуют каталог. Старый verify/manifest=1
не принимает этот формат. launcher_api=2 — отдельный протокол; его явные
офлайн-команды и запуск описаны ниже, обычный путь format=1 не переключён.

Будущий порядок действий:

1. Под блокировкой сохранить согласованный снимок выбора компонентов и его ревизию.
2. Проверить подпись каталога и построить план по разрешённым ID.
3. Скачать только нужные архивы, проверить их длину и SHA-256.
4. Собрать в новом каталоге полный комплект ядра и нужных языков. Пакет языка
   может писать только свои известные файлы locales; пересечения с другим
   пакетом, DLL/EXE, ссылки и обход путей запрещены.
5. Применить ограничения распаковки к сумме всех пакетов, а не отдельно к каждому.
   Отправная граница нынешнего клиента: 512 МиБ скачивания, 2 ГиБ распаковки,
   4096 файлов. Каталог также требует отдельного малого лимита.
6. Сохранить подписанный receipt и снимок выбора в кандидате; переключить
   указатель на весь комплект атомарно при следующем запуске.
7. Подтвердить запуск и выбранную локализацию, затем очищать только неиспользуемые
   управляемые копии по существующей политике блокировок и безопасного rollback.

Изменение языка оформляется новой транзакцией даже для того же CEF, а не
редактированием ресурсов работающего ядра. После отмены, обрыва сети, ошибки
подписи или нехватки места текущий комплект остаётся доступен. Смена выбора
во время загрузки не должна выдавать старый план за выполненный новый.
В receipt требуется связать выбранные пакеты с каталогом; локальный JSON сам
по себе не подтверждает подлинность установленного комплекта.

## Стоимость и проверки

Для ru+en-US измерена экономия файлов локализаций 46,77 МиБ относительно всех
языков CEF 154.0.34. Это не оценка всего инсталлятора и не обещание ускорения.
Планирование сейчас использует существующие serde/serde_json; новых зависимостей,
служб, таймеров и сетевых соединений нет. Команда работает по запросу. Размер
программы, время запуска, RAM и CPU нового планировщика отдельно не измерены.
Будущие установка/обновление потребуют временного места под архивы и новый
полный комплект; UI не должен ждать распаковку.

Выполненные проверки фиксируются в TASKS.md. До включения доставки нужны тесты:
неподписанный каталог, чужая версия языкового пакета, отсутствующий выбранный
язык, подмена пути/хеша, пересечение файлов, суммарные лимиты, повреждённый выбор,
смена выбора во время загрузки, прерванная установка, rollback и восстановление.
Дополнительно — реальные ru/en-US сообщения, PDF и запуск со свежими профилями.
Результаты уже выполненного языкового smoke: [CEF_MODULARITY.md](CEF_MODULARITY.md).

Для текущего этапа прошли 19 тестов: 7 каталога, 3 конфигурации и 9 прежнего
обновлятора; clippy с запретом предупреждений, rustfmt и diff-check. Негативный
тест обнаружил и после исправления подтвердил отказ от неизвестного поля у
объекта core. Реальный запуск диагностической команды с неподписанным каталогом
завершился ошибкой без изменения входных файлов. Это не независимый аудит и
не испытание реальной модульной установки.

## Формирование отдельных архивов

Добавлен `scripts/package-components.py`: локально создаёт core, en-US и ru
в новом каталоге, затем `catalog.unsigned.json` и `inspection.json`. Ничего
не подписывает, не загружает в сеть и не меняет входной bundle. Названия URL
в неподписанном каталоге — предполагаемое место будущего выпуска, а не
подтверждение наличия файлов в GitHub.

Пример для проверенной исходной Windows-поставки:

```powershell
python scripts/package-components.py --bundle target/core-final-bundle/core/seed --output .local/component-packages-new --sequence 1 --min-safe-sequence 0 --engine-version 154.0.34+g14c5a08+chromium-154.0.8037.98 --release-tag component-test
```

Нужен настоящий `dist/LICENSES-RUST.html` соответствующей сборки (можно указать
через --licenses). sequence=1 в примере — тестовый номер, не номер выпуска
действующего канала. engine-version задаётся сборочной системой; скрипт не
запускает DLL и не определяет её версию. Достоверное происхождение бинарников
и соответствие объявленной версии остаются ответственностью сборки и будущих
runtime-проверок. Сам хеш адаптера берётся из проверенных байтов архива core.

Ядро формируется по явному списку runtime-файлов закреплённого CEF: сохраняются
sandbox bootstrap, адаптер, CEF, ICU, V8 snapshot, общие ресурсы, GPU-библиотеки
и лицензии. В ядре нет locales, PDB, import library, CMakeLists, archive.json,
блокировки работы, профилей и журналов. Для будущей версии CEF список нужно
повторно проверить: это не универсальное обещание совместимости любого CEF.
PDF и код доступности остаются в libcef.dll; это разделение поставки, не
функционально урезанная собственная сборка Chromium.

Языковой архив содержит ровно четыре файла своего языка в locales. Имена
компонентов не пересекаются. Отсутствие обязательного файла отвергается до
создания output; существующий output не перезаписывается. Ссылки/reparse points
во входных файлах и их родителях запрещены. Время/владелец/порядок файлов tar
и заголовок gzip фиксированы, чтобы одинаковые входы давали одинаковые архивы.

После упаковки каждый архив читается повторно без извлечения на диск:
проверяются список и тип записей, отсутствие дубликатов, размер распаковки,
SHA-256 каждого файла против источника, размер и SHA-256 архива. Каталог
записывается только после успешных проверок всех пакетов и суммарных лимитов.
При сбое может остаться частичный новый output; он не является готовым выпуском
и автоматически не удаляется. Потребитель должен доверять только подписанному
каталогу и повторно проверять реальные архивы — отчёт производителя не заменяет
клиентскую проверку.

Локальные результаты 2026-10-20, `.local/component-packages-2026-10-20/`:

| Пакет | Скачивание, байт | Размер файлов, байт | Файлы |
|---|---:|---:|---:|
| core | 173 919 165 | 381 703 815 | 23 |
| en-US | 193 947 | 589 666 | 4 |
| ru | 268 624 | 1 204 779 | 4 |

Итого для ru с резервным en-US: 174 381 736 байт архивов (166,30 МиБ).
Это размер конкретного проверенного набора, не оценка будущего установщика.
Экономия языковых файлов 46,77 МиБ подтверждена отдельно; напрямую сравнивать
этот итог с прежним полным сетевым пакетом без выравнивания состава нельзя.
libcef.dll в архиве имеет прежний SHA-256
`e3da6707a840a8f33f565e011542169fd51aaa5218603eb7a89039fb16d79ae7`.

Проверки этапа: 6 тестов Python (разделение, воспроизводимость, ошибочные входы,
сохранение существующего output, лишние/повторные записи, traversal, подмена
содержимого и ссылки) и 20 тестов Rust. Новый сквозной тест запускает упаковщик
на синтетических файлах, подписывает его каталог временным тестовым ключом,
передаёт настоящему Rust verifier и сверяет размеры/хеши архивов. Для этого теста
нужен Python в PATH; это инструмент тестирования, не зависимость браузера.
Clippy, rustfmt, diff-check пройдены; выполнено ручное ревью состава и границ.

На данном этапе собранные реальные архивы не устанавливались и браузер из них
не запускался. Рабочий ключ и канал обновлений не использовались. Следующий
ограниченный этап — клиентская проверка состава реальных архивов и сборка
из них нового комплекта, до подключения транзакционного переключения.

## Клиентская проверка и офлайн-сборка

В `updater/src/packages.rs` реализован `VerifiedCatalog::stage_local`.
План получается из проверенного каталога и конфигурации; неподписанные
метаданные или произвольный PackagePlan не являются входом этого метода.
Он не скачивает пакеты, не пишет state/receipt и не выбирает активное ядро.

Сначала проверяются реальные размеры/SHA-256 всех выбранных архивов. Файлы
проверяются и читаются через те же открытые дескрипторы; на Windows запрещён
совместный доступ для записи/удаления. Дескрипторы сохраняются до чтения архивов.
Затем создаётся только новый каталог: существующий, даже пустой, не используется.
Родитель каталога должен принадлежать вызывающей стороне и не изменяться
параллельно. Ссылки и reparse points во входных путях/родителях отвергаются;
созданные промежуточные каталоги также проверяются.

Разрешён точный список 23 файлов ядра закреплённого Windows-профиля и по четыре
файла на язык. Любой другой путь, DLL в языковом пакете, ссылка, каталог как
запись tar, псевдоним регистра, дубликат или пересечение файлов отвергаются.
Отсутствие обязательного файла блокирует успех. Лимиты 4096 файлов и 2 ГиБ
относятся ко всему комплекту, а не отдельно к языкам. Потоки распаковки доходят
до конца gzip для проверки CRC; за концом tar допускается только ограниченное
нулевое заполнение. Хеш реально собранного адаптера сверяется с каталогом.

Каждый файл создаётся с create_new и синхронизируется перед успехом. При ошибке
новый каталог может остаться частичным: повторно использовать или запускать его
нельзя. Действующие файлы и пользовательские профили метод не изменяет.
Это ещё не транзакционная установка и не подтверждение работоспособности CEF.

Команда для каталога, подписанного доверенным ключом:

```powershell
./updater/target/release/cm-update.exe --stage-components installation.json signed-catalog.json archives new-output 10 8
```

Как и у --catalog-plan, последние два числа — явные диагностические параметры
highest/min-safe. Рабочий канал эту команду автоматически не вызывает. Любая
подмена пакета отклоняется до создания выходного каталога; ошибка его состава
может обнаружиться уже после частичной распаковки.

Проверки: обычная серия 20 Rust-тестов прошла; сквозной тест дополнен сборкой
ru (31 файл), en-US (27 файлов, без ru), отказом от существующего output,
подменённого архива, языкового пакета с DLL, traversal, ссылки, неполного пакета,
дубликатов и размера распаковки сверх лимита. Отдельно явно выполнен обычно
пропускаемый тест `assemble_real_component_archives_offline` с реальными
архивами CEF и временным тестовым ключом в памяти. Рабочий закрытый ключ не читался.
Clippy, rustfmt, diff-check и ручное ревью пройдены.

Результат реальной сборки: `.local/component-client-stage-2026-10-20/`,
31 файл, 383 498 260 байт (три пакета, ru+en-US). Отчёт:
`.local/component-client-stage-2026-10-20.report.json`. Независимым проходом
пересчитаны SHA-256 всех 31 файлов против отчёта производителя, лишних файлов нет.
Для повторения нужен новый выходной путь:

```powershell
$env:CHROMINIMUM_COMPONENT_TEST_INPUT = (Resolve-Path .local/component-packages-2026-10-20).Path
$env:CHROMINIMUM_COMPONENT_TEST_OUTPUT = Join-Path (Get-Location).Path '.local/component-client-stage-new'
cargo test --manifest-path updater/Cargo.toml --locked --release --test producer assemble_real_component_archives_offline -- --ignored --nocapture
```

Тест не сохраняет временный ключ и не активирует комплект. Браузер из собранного
каталога пока не запускался. Следующий ограниченный шаг — HTML/JavaScript и PDF
из этого комплекта в отдельном тестовом профиле вне ограничений среды агента;
затем подписанный receipt, восстановление и атомарное переключение.

## Runtime-проверка собранного комплекта

## Локальная транзакция модульного комплекта

2026-10-20 добавлен библиотечный модуль `updater/src/component_install.rs`.
Он работает в существующем приватном корне установки под той же блокировкой
core-update.lock, но использует отдельные component-state.json и component-core.
Обычный загрузчик, CLI сетевого обновления и core-state.json не переключены
на этот протокол. Это локально проверенный механизм, не готовая доставка.

prepare проверяет свежий подписанный каталог относительно highest/min-safe,
собирает комплект в новом случайном staging-каталоге и сохраняет receipt:
исходный подписанный каталог плюс проверенный снимок конфигурации. Идентификатор
комплекта — SHA-256 байтов receipt. Таким образом, разные наборы языков могут
существовать для одной sequence без изменения работающих ресурсов. Receipt
синхронизируется, каталог публикуется переименованием, затем атомарно записывается
pending и неизменяемый назад порог безопасности через существующий atomic_write.

Если процесс прервался после публикации каталога до записи state, повторная
подготовка сравнивает все файлы, их размеры/хеши и структуру с заново проверенным
staging, не перезаписывая найденный комплект. Несовпадение блокирует восстановление.
Оставшиеся staging-каталоги после ошибок автоматически не удаляются. Модель
проверяет прерывания процесса, но не является доказательством стойкости ко всем
вариантам потери питания и повреждения файловой системы.

select проверяет ID и подпись receipt. Для ранее установленной копии срок
каталога проверяется на подписанный issued, а не на текущую дату; истечение
срока не отключает уже принятую установку. Кандидат выбирается только один
раз с записью attempted до возврата результата. Возвращаются ID, sequence,
язык и случайный одноразовый token пробного запуска. confirm принимает только
соответствующие pending ID/token после select и атомарно переносит pending в
active. Старая или чужая попытка подтверждения отклоняется.

Если следующий select видит попытку без подтверждения, он очищает pending и
выбирает предыдущий подтверждённый комплект только выше signed security floor.
Если безопасного active нет, выбор завершается ошибкой. Повреждённые state
и receipt не сбрасываются молча; требуется восстановление/ремонт установки.
Это fail-closed, а не обещание автоматического исправления любых повреждений.
При select проверяется receipt, но не хешируется заново всё установленное ядро.
Предполагаются приватный корень и отсутствие конкурентной подмены файлов тем же
пользователем; это не защита от владельца аккаунта, изменяющего всю установку.

Синтетический сквозной тест проверяет prepare/select/confirm, отклонение
неверного и устаревшего token, подтверждённый active, смену языка в той же
sequence, безопасный откат, отказ от отката ниже нового floor, восстановление
публикации до state commit и подменённый receipt. Отдельный тест проверяет
повреждённый state и конфликт блокировки без сброса данных.

Пересозданы реальные пакеты с проверенным smoke-адаптером:
`.local/component-packages-fixed-2026-10-20/`, тестовая sequence=2, min-safe=0.
core — 173 921 592 байта, en-US — 193 947, ru — 268 624;
сумма — 174 384 163 байта. SHA-256 адаптера:
`4da41b81dab0f30ea0eae195822c8350580db2c226cb7049ea14e44272f9b3e7`.
Старые архивы сохранены. Каталог по-прежнему неподписанный вне теста.

Обычно пропускаемый тест явно запущен на этих архивах с временным ключом в
памяти и выполнил реальную запись нового комплекта и атомарного состояния:
`.local/component-transaction-fixed-2026-10-20/`. Отчёт рядом:
`.local/component-transaction-fixed-2026-10-20.report.json`.
В полученном runtime 31 исходный файл и receipt; независимым проходом сверены
хеши всех 31 файлов, active соответствует отчёту, pending отсутствует,
core-state.json не создан. Тестовый ключ не сохранён; эти receipts не доверены
рабочему ключу и не предназначены для запуска действующим загрузчиком.

Для повторения требуется новый существующий приватный root, создаваемый тестом:

$env:CHROMINIMUM_COMPONENT_TEST_OUTPUT = Join-Path (Get-Location).Path '.local/component-transaction-fixed-new'
$env:CHROMINIMUM_COMPONENT_TEST_TRANSACTION = '1'

Обычная серия: 21 Rust-тест прошёл, реальный тест — отдельно. Пройдены clippy,
rustfmt и diff-check, выполнено ручное ревью state/receipt и путей восстановления.
Новых зависимостей, службы, сетевого канала и изменений браузерного запуска нет.
Файлы и подписи обрабатываются по запросу; время, CPU/RAM и дисковые пики этой
транзакции отдельно не измерены. Подготовка хранит ещё одну полную копию runtime.

Подтверждение в реальном тесте вызвано самим тестом после select — приложение
не запускалось и не сообщало healthy. Получение trial token браузером, фактическая
загрузка выбранного runtime, передача языка, подтверждение после загрузки,
удержание lease и миграция старой установки ещё не подключены. Очистка старых
модульных копий также не реализована. Следующий этап — интеграция этого протокола
с загрузчиком на изолированной установке, до сетевой доставки и инсталлятора.

## Настоящий запуск через модульный загрузчик

2026-10-20 добавлены явные офлайн-команды:

```powershell
cm-update.exe --prepare-components installation-root installation.json signed-catalog.json archives
cm-update.exe --launch-components installation-root --url=https://example.com/
```

Первая команда проверяет каталог встроенным публичным ключом и готовит
кандидата через component_install. Вторая выбирает runtime, удерживая блокировку
state до получения shared lease каталога. Затем запускает sandbox bootstrap,
передавая отдельный каталог профиля, идентичность комплекта и язык из receipt.
Аргумент smoke test не может переопределить управляемый язык. Новые команды
не заменяют обычный запуск и не мигрируют core-state.json.

Для готовности создаётся pipe stdout дочернего процесса. Загрузчик ждёт ровно
сообщение с выбранным ID и случайной меткой этого запуска; количество читаемых
байтов ограничено 8192, ожидание — 60 секунд. Browser process отправляет сообщение
из существующего callback первой загрузки main frame или страницы ошибки.
Это подтверждение запуска движка, не гарантия успешности произвольного сайта,
TLS-проверки или всех функций PDF. Trial token остаётся в загрузчике и применяется
при confirm только после совпадения сообщения; страницы не получили нового
интерфейса IPC или исполнения native-команд.

Браузер получает свой shared lease до сообщения готовности. После сообщения
загрузчик освобождает свой lease и в обычном режиме выходит; в smoke-режиме
ждёт штатного завершения, чтобы вернуть код ошибки тесту. Ожидается только
событие процесса, постоянной службы или production-опроса не добавлено.
При таймауте загрузчик выдаёт ошибку и не принимает candidate; дочерний процесс
не убивается принудительно. Новый select не откатывает pending, пока его lease
удерживается живым процессом. Этот конкурентный случай проверен сквозным тестом.

В component_ready выделена отправка сообщения без panic при закрытом pipe.
Отдельные два std-only теста проверяют точный протокол и BrokenPipe; они запускаются
через rustc --test без загрузки CEF. Обычный браузер без модульных переменных среды
использует прежний путь healthy. Модульный режим не включает старые сетевые проверки:
кнопка обновлений отключена с понятным сообщением, поскольку новый канал ещё не
подключён. Это не политика отказа от обновлений для будущего продукта.

Проверена реальная связь launcher/browser и выбор локализации. PDF на этой новой
DLL, HTTPS/TLS, фактические sandbox-токены и визуальная приёмка не выполнялись.
Инсталлятора, миграции старой установки, сетевой загрузки модульного плана и
очистки старых component-core ещё нет. Следующий ограниченный этап — загрузка
только выбранных пакетов с сохранением существующих подписей/лимитов и передачей
результата проверенному prepare, до публикации нового канала.

## Загрузка выбранных пакетов, 2026-10-20

Реализована явная команда загрузчика:

```text
cm-update.exe --fetch-components <existing-private-root> <config.json> <signed-catalog.json> <new-cache-directory>
```

Каталог пока передаётся локальным файлом, а выбранные архивы загружаются по его
подписанным HTTPS URL. Команда проверяет подпись, срок, sequence и сохранённый
порог безопасности до сетевых запросов. При pending отказывает до загрузки.
Блокировка установки не удерживается во время сети; перед prepare срок и состояние
проверяются повторно под блокировкой. Успешная подготовка создаёт pending;
переключение active по-прежнему требует запуска и readiness браузера.

Используется существующий ureq 3.4.2/rustls без новых зависимостей и без отключения
проверки сертификатов. HTTPS-only применяется также к перенаправлениям; API и
реализация проверены в локальном исходнике закреплённой зависимости. Таймауты:
600 секунд на запрос целиком, 15 на соединение, 30 на получение ответа.
Архивы скачиваются последовательно, общий подписанный размер не выше 512 МиБ.
Буфер хеширования — 64 КиБ; весь архив в RAM не помещается. Постоянной службы нет,
обычный запуск и старый канал эту команду не вызывают.

Кэш должен быть новым каталогом внутри существующего приватного родителя.
Проверяются небезопасные имена Windows и коллизии без учёта регистра.
Данные идут в download.part; размер и SHA-256 проверяются потоково до переименования.
При ошибке удаляется только созданный этой попыткой partial. Ранее проверенные
архивы остаются; автоматической очистки/докачки нет. Далее stage_local повторно
проверяет архивы перед распаковкой. Профили и active не затрагиваются загрузкой.

Выполнены локальные HTTP-тесты с настоящим TCP-сервером и тестовым транспортом,
который только внутри cfg(test) отображает подписанные GitHub URL на loopback:

- en-US: два запроса, ядро и английский язык; ru не запрашивается;
- ru: три запроса, ядро, английский fallback и русский язык;
- разрыв ответа, неверный SHA-256 и превышение размера отклонены без готового
  архива/partial и без изменения контрольного файла состояния;
- существующий кэш не используется; неверная подпись не создаёт новый кэш.

Все 24 обычных теста обновлятора прошли (один отдельный real-CEF тест пропущен
по умолчанию), clippy с -D warnings, rustfmt и Release-сборка прошли.
Размер локального Release cm-update.exe: 2 379 776 → 2 390 016 байт, +10 240 байт
относительно файла перед этой задачей. Это сравнение артефактов, не чистая парная
сборка исходников. CPU/RAM и время запуска сравнительно не измерялись.

Ограничения: нет сквозной проверки HTTPS/CDN → реальный CEF → readiness для этой
команды; HTTP-тесты подтверждают выбор и обработку потока, а не TLS-приёмку.
Рабочий канал, реальный ключ и установка пользователя не изменены. Инсталлятор,
загрузка самого каталога из канала, миграция и очистка старых копий остаются
отдельными этапами. Следующий шаг — сквозной тест доставки реальных архивов
через HTTPS на изолированной установке до подключения рабочего канала.

## Сквозная проверка локального HTTPS, 2026-10-20

Добавлены `scripts/serve-component-tls-fixture.py` и отдельный ignored-тест
`download::tests::real_components_over_verified_tls`. Это тестовая инфраструктура:
рабочие зависимости, настройки TLS и пути запуска приложения не менялись.
Сервер слушает только 127.0.0.1 и отдаёт только tar.gz из выбранного каталога;
сертификаты и ключи через HTTP не доступны. Новой службы в поставке нет.

Испытание выполнено в `.local/component-tls-e2e-2026-10-20` на реальных архивах
из предыдущего launcher-E2E, CEF 154.0.34. Локальный CA и серверный сертификат
с SAN DNS:localhost созданы OpenSSL из Git for Windows; сертификат добавлен
только в RootCerts::Specific тестового ureq-клиента. В системное хранилище
ничего не устанавливалось, проверка сертификатов не отключалась.

Тест использует существующий download_with и отображает подписанные GitHub URL
на локальный HTTPS только внутри cfg(test). Он заново подписывает каталог
общеизвестным одноразовым fixture-ключом, обновив срок, затем вызывает настоящий
prepare с этим публичным ключом. В production нет параметра для подмены URL,
доверенного CA или подписывающего ключа.

Результаты:

| Проверка | Результат |
|---|---|
| Сервер без доверия к тестовому CA | Отказ TLS |
| Доверенный CA, обращение к 127.0.0.1 вместо localhost | Отказ проверки имени |
| HTTP вместо HTTPS | Отказ HTTPS-only |
| Английский выбор | Загружены core 173 924 198 + en-US 193 947 байт, без ru |
| Русский выбор | Загружены те же два архива + ru 268 624 байт |
| Проверка архивов и prepare | Для двух установок созданы pending, active ещё null |
| Запуск en-US через тестовый launcher | Код 0, readiness/confirm, «Please fill out this field.» |
| Повторный запуск ru | Код 0, «Заполните это поле.», HTTP/JS и shutdown прошли |

В журнале HTTPS ровно пять GET: core/en-US, затем core/en-US/ru. Браузерные
прогоны не изменили payload/receipt. После запусков обе установки active с
pending=null. Рабочая версия загрузчика отдельно проверена: каталог fixture-ключа
отклонён с `Catalog signature invalid`; исходный public-key.hex не изменён.
Временный launcher лежит только в каталоге этого теста. TLS-сервер остановлен,
его два закрытых ключа удалены после испытания.

Первый русский smoke не прошёл: при параллельной работе тестовых процессов
не было запроса страницы до ограничителя времени, затем ERR_ABORTED, код процесса 0.
Повторный отдельный запуск прошёл. Причинная связь с параллельностью не доказана.
Readiness подтверждает запуск движка также при ошибке навигации, поэтому active
был подтверждён уже первой попыткой, а успешная локализация — только повторной.
Первый GET в успешных прогонах наблюдался через 30,3 и 19,9 с. Проблема задержек
HTTP остаётся открытой; изменение smoke-таймеров и исправление движка не заявляются.

Артефакты: `tls-result.json`, `requests.jsonl`, `run-en-US/result.json`,
`run-ru/result.json` (неуспешный), `run-ru-retry/result.json` (успешный),
`installation-*/component-state.json`. Результат ignored-теста: 1 passed,
около 60,5 с с загрузкой, повторным хешированием и распаковкой двух комплектов;
это не сравнительный бенчмарк. Повторно прошли 24 обычных теста, clippy
с -D warnings, rustfmt, синтаксис Python, Release-сборка и diff-check.

Для повторения нужны свежий приватный каталог fixture, origin.txt от сервера,
ca.der, server.pem/server-key.pem и исходный catalog.unsigned.json. Сертификат
сервера должен быть подписан этим CA с SAN DNS:localhost и serverAuth.
После запуска сервера:

```powershell
$env:CM_COMPONENT_TLS_FIXTURE = '<absolute-new-fixture-directory>'
cargo test --manifest-path updater/Cargo.toml --offline --lib real_components_over_verified_tls -- --ignored --nocapture
```

Для launcher-проверки копия исходников загрузчика собирается с созданным тестом
public-key.hex в отдельный target-dir. Его нельзя подставлять в рабочую сборку.
Затем smoke-component-bundle.py запускается с --launcher, --installation-root,
--case locale и соответствующим --expected-locale на созданных installation-*.

Границы: это сквозное испытание библиотечного загрузчика через тестовый транспорт,
а не успешный production --fetch-components с настоящим GitHub/CDN. Публичные URL,
доставка каталога, миграция и инсталлятор ещё не проверены/не реализованы.
Новых функций доступности/орфографии или вырезанной PDF-сборки здесь нет.
Следующий ограниченный шаг — диагностика задержки первого HTTP-запроса перед
дальнейшей интеграцией установки и обновления.

Диагностика выполнена следующим этапом: [HTTP_STARTUP_DIAGNOSIS.md](HTTP_STARTUP_DIAGNOSIS.md).
Воспроизведённый длинный интервал связан с дисковой инициализацией нового профиля
на HDD; при том же runtime и новом профиле на NVMe первый GET занял около 0,28 с.
Это не исправление CEF или смена production-пути профиля; подробности и пределы
вывода приведены в отчёте.
