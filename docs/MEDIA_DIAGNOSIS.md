## Вывод и границы

Отсутствие поддержки указанных H.264/AAC подтверждено для этой поставки.
Это вероятное объяснение сбоя, если плеер использует такие кодеки.
Работа YouTube согласуется с поддержкой альтернативных форматов, но кодек
его фактического потока здесь не определялся. API capability — не проверка
успешного декодирования файла. Причина конкретной загрузки VK ещё не доказана:
не исключены ошибки сети, авторизации или JavaScript.

Стандартный CEF не включает proprietary codecs; первичный источник:
[инструкция Google по сборке CEF](https://support.google.com/webdesigner/answer/10043691?hl=en).
Сборка с ними требует иных GN-параметров и рассмотрения условий распространения.
Подмена DLL от другого браузера и отключение sandbox/TLS не выполнялись.

Следующий шаг: получить ошибку плеера/формат потока из авторизованной страницы
без сохранения cookies и паролей. Если H.264/AAC подтвердятся, отдельно согласовать
вариант ядра, стоимость сборки/поставки, ожидаемые CPU/RAM/запуск/сеть и замеры,
затем проверить реальное воспроизведение на отдельном профиле. Ядро и установленный
браузер этой диагностикой не изменены.

## Разрешение MIDL-блокера

На новом checkout ошибка воспроизведена отдельно. Четыре текстовых файла
совпали побайтово. В `tracing_service_idl.tlb` длиной 2736 байт различались
10 байт: два указателя bucket таблицы имён и 16-битный хеш имени
`SystemTraceSessionLib`. `LHashValOfNameSys` воспроизводит низкие 16 бит:
LCID 1033/0 → DBE5 (эталон), LCID 1049 → DC42 (локальный MIDL).
Системная/пользовательская LCID машины — 1049. Сам TLB декларирует 1033.
Первичный API: [Microsoft LHashValOfNameSys](https://learn.microsoft.com/en-us/windows/win32/api/oleauto/nf-oleauto-lhashvalofnamesys).

Документированный `/lcid 1033` не устранил хеш библиотеки. Проба атрибута
в IDL также не дала побайтового совпадения; исходный IDL восстановлен.
Первый вариант [сборочного патча](../patches/chromium/0002-deterministic-midl-name-hash.patch)
нормализовал только целиком известный результат MIDL
SHA-256 `5f51521224f2ad3bdf5a43bb89a3b3ff71c337acbf85c4696a9a75ce6416dad3`.
После изменения трёх metadata-полей обязательный SHA-256 результата —
`e848b4dc9b8e4947c22251bf1743a16062836646165a9d3c56654d5697e1c824`,
точно как у исходного upstream TLB. Штатное сравнение оставалось активным.

Первое и повторное применение сборочного патча прошли, хеш Python-скрипта
проверен. После этого штатная MIDL-команда завершилась 0: все пять выходных
файлов совпали с эталоном. Это ещё не сборка/запуск libcef.
Сравнение до исправления: `.local/media-build-2026-10-21/midl-comparison.json`.

Полная компиляция затем выполнила 21486 шагов за 58m44s и остановилась на
MIDL updater_legacy_idl (46261 оставшихся шага по отчёту сборщика). Заголовок
и i.c совпали; в TLB снова различались только хеш имени и связанные bucket.
Вместо отдельных бинарных исключений патч заменён общим пересчётом имени
библиотеки по LCID из заголовка через LHashValOfNameSys и перестроением таблицы
поиска. Обрабатывается только подтверждённый вариант хеша пользовательской LCID;
другие неожиданные хеши отклоняются. Используются ASCII-имена и проверяемый
MSFT-формат. Описание структуры: [Wine typelib_struct.h](https://raw.githubusercontent.com/wine-mirror/wine/master/tools/widl/typelib_struct.h).
Системные DLL загружаются только из System32, локаль Windows сохраняется.

На обоих известных TLB исправленный результат побайтово равен upstream;
канонический результат сохраняется без изменения. Первое/повторное применение
нового патча и отказ на изменённом Python-исходнике прошли на отдельной фикстуре.
Проверки: `.local/media-build-2026-10-21/generic-midl-validation.json`,
`generic-midl-results.json`. Текущий SHA-256 helper после патча:
`00031ff655aa700f76c33a59f93417e6b4f7a4c71b43f8aa9dbf171587b91cef`.
Рецепт теперь проверяет все MIDL action из default toolchain без testonly
до возобновления полной компиляции. Готового нового runtime пока нет.

Все 16 таких MIDL-целей прошли штатное сравнение: 24 шага за 53,14 с,
без ошибок. Список: `C:\cm-media154\midl-preflight-targets.json`.
Полная компиляция возобновилась с сохранёнными объектами, без новой загрузки.

CEF получен без истории на точном commit 14c5a08 (Git-pack 4142376 байт),
upstream automation запускается с `--no-cef-update` после проверки HEAD.
Исходники Chromium, 245 зависимостей и 119 runhooks подготовлены.
Из-за shallow CEF checkout генерируемая строка версии может отличаться от
официальной 154.0.34; тождество исходников определяется commit, а фактические
строка версии/API/совместимость будут проверены после компиляции.

сравнение не изолирует стоимость одних кодеков. Скрипт подготовлен, замеры

7594.9 МиБ private bytes, 7743.0 МиБ сумма working set; это не пиковый замер.
Он описывает расходы компиляции и не является измерением ресурсов браузера.

python tools/make_distrib.py --output-dir=C:/cm-media154/media-distrib --minimal --ninja-build --x64-build --allow-partial --no-archive --no-symbols --no-docs --no-format

Затем из корня проекта, подставив фактический каталог distribution:

python scripts/stage-media-experiment.py --distribution C:/cm-media154/media-distrib/<cef_binary_directory> --adapter .local/release-alpha7/bundle/core/seed --output .local/media-experiment-20261021

## Защита пути назначения (2026-10-22)

В существующем упаковщике исправлена неполная проверка путей: ранее ссылки
проверялись только у входных файлов. Теперь назначение и все существующие
родительские каталоги проверяются через lstat до создания файлов; symlink
и Windows reparse points (включая junction) отклоняются. Сегменты `..`
во всех трёх входных путях запрещены, чтобы не скрывать переход через ссылку
при нормализации и не обходить проверку пересечения входа и назначения.

Воспроизводимая проверка: `python scripts/test-stage-media-experiment.py -v`.
Все 6 тестов прошли на Windows: состав 23 обязательных файлов и их SHA-256,
переименование bootstrap, два optional DXC-файла, отсутствующий/пустой libcef,
сохранность существующего назначения, пересечение каталогов/`..` и настоящий
junction в родителе назначения. Последний сценарий подтвердил отсутствие
записей в целевом каталоге junction. Данные синтетические, профили не копируются.

Исправление касается только инструмента подготовки; зависимости, код браузера,
сеть, фоновые процессы и состав поставки не изменены. Замеры браузера не
выполнялись. Это предварительная проверка путей, а не защита от конкурентной
подмены каталогов другим процессом: вход и назначение должны находиться
в доверенном рабочем каталоге. Реальная упаковка, совместимость адаптера
и воспроизведение кодеков по-прежнему ждут готовой сборки CEF.

## Автоматическая проверка медиаотчёта (2026-10-22)

После успешного завершения `diagnose-media.cjs` с кодом 0 и тремя fixtures
выполнить:

```powershell
python scripts/check-media-report.py <каталог-результата-диагностики>
```

Проверка только читает `playback.json` и `smoke.log`, выводит JSON с `passed`
и причинами отказа, возвращает 0 при достаточных данных и 1 при отказе.
Для каждого из MP4, контрольного WebM и AAC обязательна ровно одна запись.
Видео требует статуса playing, времени более 0,3 с, положительного числа кадров,
readyState не ниже 2 и отсутствия media/play error. AAC требует статуса decoded,
положительных длины PCM, числа каналов, частоты и пика сигнала. Положительный
пик требуется для выбранного тестового файла со звуком, а не как общий критерий AAC.
Булевы значения, строки, NaN и Infinity не принимаются за числовые измерения.
В журнале требуется отдельная строка `shutdown_complete`.

`python scripts/test-check-media-report.py -v`: все 6 тестов прошли, включая
коды возврата CLI, ошибки/тайм-ауты, отсутствующие/повторные записи, повреждённый
JSON, ложный shutdown-маркер и некорректные числовые данные. Сохранённый реальный
отчёт `docs/reports/media-playback-alpha7-2026-10-21` отклонён ожидаемо:
MP4 содержит ошибку, AAC-наблюдения нет. Синтаксис Python проверен.

Это проверка полноты локальных наблюдений, без запуска браузера, новых
зависимостей, сети или фоновой службы. Она не устанавливает происхождение
файлов отчёта, не доказывает код завершения процесса, слышимость звука,
корректность всех кадров, sandbox/TLS/PDF или работу VK. Штатный код завершения
нужно получить от самого диагностического runner; отчёт не заменяет остальные
пункты приёмки. Реальная проверка нового CEF остаётся невыполненной.

## Контроль процесса диагностики (2026-10-22)

В `diagnose-media.cjs` исправлен жизненный цикл наблюдаемого процесса:
ошибка spawn сохраняется сразу, без отклонённого Promise, который прежде мог
оставаться без обработчика во время ожидания CDP. Ожидание port-файла и
поиск страницы теперь прекращаются с явной ошибкой при раннем выходе процесса.
Если port-файл не появился за отведённые 15 с, выводится тайм-аут с PID.

После завершения медиапроб ожидание штатного выхода ограничено 45 с.
При превышении runner возвращает ошибку с PID и снимает удержание дочернего
процесса в Node event loop (`unref`); сам процесс не убивается, его отсутствие
не утверждается. Маркер `shutdown_complete` проверяется как отдельная строка,
а не произвольная подстрока журнала.

Проверки: `node --check scripts/diagnose-media.cjs` и
`node --test scripts/test-diagnose-media.cjs` прошли. Все 5 тестов успешны:
ENOENT, ранний exit=7, уже завершившийся exit=0, тайм-аут с PID/unref
на имитации процесса и настоящий запуск CLI с отсутствующим exe.
CLI вернул 1 примерно за 180 мс без capability-отчёта и необработанного Promise.
Тесты запускали только короткие Node-процессы, CEF и профили владельца не трогали.

Это исправление диагностического инструмента; код браузера, зависимости,
поставка и фоновые службы не менялись. 45 с — лимит только финального ожидания,
не всего сценария. На этом этапе общего watchdog ещё не было; он добавлен
следующим изменением ниже. При ошибке диагностики возможен оставшийся
smoke-процесс до его собственного штатного закрытия. Реальный прогон нового
CEF остаётся следующим этапом после компиляции.

## Общий лимит медиадиагностики (2026-10-22)

В CLI добавлен общий watchdog на 120 с с начала сценария. Он охватывает
асинхронное ожидание CDP/WebSocket, медиапробы и финальное закрытие.
При срабатывании синхронно выводится ошибка с PID наблюдаемого процесса,
Node-runner завершается кодом 1. Это не успешная приёмка даже при наличии
частичного playback.json. Таймер не может прервать синхронную блокировку
event loop, например зависшее чтение файла на уровне ОС.

Освобождение ресурсов выполняется также при обычном успехе или ошибке:
child снимается с удержания event loop, CDP-сокет закрывается, loopback-сервер
закрывает соединения и прекращает слушать. Общий таймер удаляется.
По тайм-ауту завершается только процесс диагностического Node-runner;
браузер не убивается. Его возможный остаточный процесс необходимо учитывать
по выведенному PID, отсутствие процессов такая проверка не подтверждает.

`node --check scripts/diagnose-media.cjs` и
`node --test scripts/test-diagnose-media.cjs` прошли: все 7 тестов успешны.
Новые проверки используют отдельный Node-процесс с незавершающимся Promise
и настоящим loopback TCP-сокетом (тестовый лимит 100 мс), а также проверяют
снятие таймера после успеха и исключения. Подключение настоящего CDP и новый
CEF не запускались. Зависимости, код браузера, состав поставки и фоновые
службы не менялись; таймер существует только при ручном запуске диагностики.
