## Панель навигации в fullscreen — 2026-10-22

Владелец подтвердил воспроизведение hdrezka в media preview, но показал оставшуюся
панель навигации над полноэкранным видео. В AppWindow не было обработчика
`on_window_fullscreen_transition`: CEF переводил окно в fullscreen, а добавленная
нами панель оставалась видимой. В закреплённом `cef/tests/cefclient/browser/views_window.cc`
OnWindowFullscreenTransition явно скрывает top controls.

Панели назначен стабильный native View ID; обработчик скрывает её при входе,
восстанавливает при выходе и переразмечает окно. При входе фокус передаётся
BrowserView. RefCell borrow освобождается до вызовов CEF; дополнительных
постоянных ссылок на View нет. Учтены две фазы macOS по образцу cefclient,
но Linux/macOS этой серией не проверялись. CEF и настройки безопасности не менялись.

`scripts/test-fullscreen.cjs` проверяет на своей loopback-странице и свежем профиле
реальные fullscreen/viewport через CDP. Старая DLL дала 2560×1396 на экране
2560×1440 — 44 пикселя оставались панели; тест ожидаемо завершился с ошибкой.
Новая DLL дважды дала 2560×1440 и восстановила прежний viewport 1084×677.
Отдельно повторены выход через document.exitFullscreen и через Escape.
Все успешные прогоны закрылись с кодом 0 и shutdown_complete. Первая проба с
ожиданием fullscreen Promise дала CDP timeout и не засчитана; проверка использует
асинхронное наблюдение состояния. В тестовом runner есть общий лимит 120 с.

MP4/WebM/AAC и проверка media-отчёта прошли на новой DLL. Rustfmt, Release и
Clippy с -D warnings прошли. Данные: `docs/reports/alpha8-fullscreen-20261022/`.
Владелец после применения патча подтвердил нормальную работу fullscreen hdrezka
2026-10-22; другие устройства/DPI этой проверкой не покрыты.

Хеши всех файлов CEF прежние; из 25 runtime-файлов изменён только chrominimum.dll.
DLL 780288 → 781824 байта (+1536). Новых зависимостей, процессов, таймеров или сети
продукта нет; ожидаемые расходы обработчика — только смена видимости и layout
по событию. RAM/CPU/старт отдельно не переизмерялись, прежние расходы custom CEF
сохраняются. Полная компиляция CEF не запускалась.

Патч для существующего preview:
`dist/ChroMinimum-0.0.1-alpha.8-fullscreen-fix.zip`, 365063 байта,
SHA-256 `70c149984e71e4f9a80919ddf8634ca0607fb417dda94f29f9b4e17dc58f14e7`.

## About и восстановление окна — 2026-10-22

По согласованию владельца About дополнен существующим логотипом, ссылками
https://chrominimum.download и https://github.com/SargeMadovsky/ChroMinimum,
версиями оболочки и CEF и датой выхода alpha.7 — 21.10.2026
([материалы выпуска](RELEASE_ALPHA7.md)). При следующем выпуске дату нужно
обновить вместе с версией. Ссылки по нажатию открывают обычное окно ChroMinimum.
About центрируется в рабочей области экрана по внешней рамке.

Причина ошибки состояния подтверждена исходником: сохранялись текущие bounds
без признака maximized. Теперь на Windows GetWindowPlacement возвращает обычные
размеры даже при закрытии развёрнутого/свёрнутого окна; физические пиксели
переводятся в CEF DIP. Файл window-size содержит `width height normal|maximized`;
старые два числа читаются как обычное окно. Восстановление через initial_bounds
использует внешние размеры без повторного добавления рамки. При запуске окно
показывается обычным или развёрнутым, даже если закрывалось свёрнутым.
Позиция не сохраняется. Smoke не читает и не перезаписывает этот файл.

Проверено на отдельной Windows Release-копии с новыми временными профилями:

- About открыт через меню; снимок просмотрен, все элементы видны. Центр внешней
  рамки отличается от центра рабочей области на 0 px по X и 0,5 px по Y.
- 920×680 восстановлены после перезапуска. Повторная запись файла, 980×720,
  закрытие maximized, minimized и maximized→minimized прошли: обычные размеры
  сохранены, развёрнутое состояние восстановлено. Старый формат `940 690` прочитан.
- Release build, Clippy с `-D warnings` и rustfmt прошли. Стандартный smoke
  подтвердил HTML/JS, Enter/back/forward/reload и операции окна.

Первый UI-запуск в ограниченной среде не дал окна. Успешные UI-прогоны выполнены
вне неё, с сохранением sandbox браузера. Локальный сценарий и снимки находятся в
`.local/about-window-2026-10-22/`, результат окончательного прогона —
`%TEMP%/cm-about-window-final-2026-10-22/result.json`. Все тестовые окна закрыты.
Загрузка сайтов по ссылкам не проверялась; адреса и обработчик проверены по
исходнику. Linux/macOS, несколько мониторов и различные DPI не проверены.
Исправление maximized через WINDOWPLACEMENT относится к Windows.

Новых библиотек нет: у существующего windows-sys включён модуль
Win32_UI_WindowsAndMessaging. Новых постоянных процессов, опроса и сетевых
запросов при открытии About нет. DLL: 774144 → 779264 байт (+5120 байт).
RAM/CPU и сравнительное время запуска не измерены. Основная установка и
публичные артефакты не заменялись. Далее — приёмка DPI/нескольких мониторов
и включение изменений в следующий установщик.

## Второе окно about:blank

Владелец обнаружил: первый файл открывался, второе окно было пустым. Причина
подтверждена исходником закреплённого CEF: при command_line_args_disabled он
удаляет исходные аргументы до пользовательского OnBeforeCommandLineProcessing.
Первое окно использовало заранее сохранённый URL, а callback relaunch читал уже
очищенный switch. [CEF 14c5a08, BasicStartupComplete](https://raw.githubusercontent.com/chromiumembedded/cef/14c5a08/libcef/common/chrome/chrome_main_delegate_cef.cc).

В браузерном процессе теперь восстанавливается только собственный заранее
разобранный URL для штатного ProcessSingleton/relaunch. command_line_args_disabled
остаётся включён; произвольные Chromium-флаги этим не восстанавливаются,
в дочерние процессы URL не добавляется. Sandbox/TLS-настройки не ослаблялись.

Прежний тест ошибочно принимал два окна и два события загрузки за успешное
повторное открытие; about:blank тоже удовлетворял этому условию. Добавлен
smoke-only журнал фактического main-frame URL и точное сравнение адреса второго
PDF. Обычный режим не пишет эти URL в smoke.log. EN TestInstall подтвердил URL
документа с кириллицей, пробелами, #/% в имени, два собственных окна и код 0.

## Список открытия Windows и Total Commander

Скриншоты владельца показывают ChroMinimum в полном диалоге и его отсутствие
в коротком каскадном меню Total Commander. Новый read-only инструмент
`scripts/inspect-file-associations.ps1` через SHAssocEnumHandlers перечислил
реальную установленную программу как Recommended=true для .html/.htm/.pdf.
Проверка использует только GetName/GetUIName/IsRecommended; назначения по
умолчанию и запуск обработчиков не выполняются.

[Windows SHAssocEnumHandlers](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-shassocenumhandlers)
различает все и рекомендованные обработчики. Регистрируемый OpenWithProgids
соответствует [инструкции Microsoft](https://learn.microsoft.com/en-us/windows/win32/shell/how-to-include-an-application-on-the-open-with-dialog-box).
Из этого не следует, что конкретное короткое меню Total Commander обязано
немедленно обновиться. Кэш/отбор самим приложением — гипотезы, причина не
установлена; восстановление именно его меню не объявляется проверенным.
Дополнительные обходные записи в реестр и изменения UserChoice не внесены.
